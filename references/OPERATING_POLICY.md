# Operating Policy

## Mode

Execution mode is **on**. The scanner (`scan-ready-issues.mjs`) remains read-only — it produces plans. The calling agent executes those plans, performing the GitHub and git mutations listed below.

## Allowed Actions

- read local repo files
- read-only `gh` calls: `gh issue list`, `gh issue view`, `gh repo view`, `gh pr list`, `gh pr view`
- `gh issue edit` — only to flip verified acceptance-criteria checkboxes (`- [ ]` → `- [x]`) and to add/remove the claim/state labels listed below
- `gh issue comment` — claim comment, AC verification report, completion comment, failure comment
- `gh issue close` — only after the linked task PR has auto-merged into the batch branch (see "Completion & Issue Close")
- `git fetch origin`, `git checkout -B <task-branch>` based on the batch branch
- `git add`, `git commit`, `git push origin <task-branch>`
- `gh pr create` against the batch branch (not main); PR body **must** contain `Closes #<issue>`
- `gh pr merge --auto --squash` against the batch branch (auto-merges once required checks pass)

## Forbidden Actions

- any mutation targeting `main` directly (no PR base = main, no merge to main, no push to main)
- `git push --force` / `git push -f` on any branch
- removing or rewriting **another** agent's claim labels or comments
- deleting branches that were not created by this run
- modifying acceptance-criteria text (only the checkbox state may change)
- ticking acceptance-criteria checkboxes for `L4` (human-only) items
- ticking acceptance-criteria checkboxes when verification did not produce concrete evidence
- bypassing test gates (`--no-verify`, skipping lint/test/build)
- closing an issue before its linked task PR is confirmed merged into the batch branch

## Comment Timeline

Every dev package gets the same audit trail on its GitHub issue. Four comment types, in order:

1. **Claim comment** — posted when the run starts and acquires the claim lock
2. **AC verification report** — posted after AC verification finishes (success path)
3. **Completion comment** — posted after `gh pr merge --auto --squash` is queued (success path)
4. **Failure comment** — posted if any step fails (replaces #2 and #3 on failure path)

All four use the same prefix:

```markdown
> *This was generated by AI during afk-agent run <run-id>.*
```

### Claim comment

Contents:

- run id
- issue number
- task branch
- batch branch
- started-at timestamp
- expected test gates (lint, test, build commands)
- AC verification plan summary (`L1 N · L2 N · L3 N · L4 N`, plus L4 items listed by name)

### AC verification report

See [`AC_VERIFICATION.md`](AC_VERIFICATION.md) for the full template. One bullet per pending AC: text, level, status (passed / failed / skipped-L4), evidence reference.

### Completion comment

Posted after `gh pr merge --auto --squash` returns and the PR is queued for auto-merge. Contents:

- run id
- PR link with auto-merge status (`auto-merge enabled, base agent/<theme-slug>`)
- waiting on which CI checks (from `gh pr checks`)
- AC tick stats: `<ticked> / <pending> AC checkboxes flipped; <L4 count> L4 items flagged for human`
- L4 items listed by name (human must verify these on the batch branch before it merges to main)
- total elapsed time (run end - run start)
- issue close strategy line: "issue will be closed by this run if auto-merge completes within 60s; otherwise the next afk-agent run will close it via reconciliation"

### Failure comment

Contents:

- run id
- failed step name (e.g. `lint`, `test`, `build`, `ac-verify:L2`)
- key error excerpt
- task branch name (left pushed for human inspection — `git fetch && git checkout <task-branch>` to inspect)
- AC tick count: **always 0** on the failure path (no boxes flipped in failed runs)
- recommended next step (remove `agent-failed` + `agent-claimed` after fixing, or escalate)

## Completion & Issue Close

GitHub's `Closes #<issue>` keyword only auto-closes an issue when the PR merges into the repo's **default branch**. Task PRs merge into the **batch branch**, not the default branch — so `Closes #<issue>` alone does not close the issue.

To give the user a prompt "this dev package is done" signal, the agent uses two mechanisms together:

1. **Eager explicit close**: after `gh pr merge --auto --squash` succeeds, the agent polls `gh pr view <pr-number> --json state` every 5s for up to 60s. If the state becomes `MERGED` within the window, the agent runs:

   ```bash
   gh issue close <issue> --comment "<completion-comment-body>"
   ```

   If the poll times out, the agent leaves the issue open and the completion comment carries the "reconciliation will close it" note.

2. **Defense in depth via `Closes #N`**: every task PR body contains `Closes #<issue>` on its own line. This builds the PR↔issue link (visible in GitHub UI) and provides a fallback close path: when the batch branch eventually merges to main, GitHub closes any still-open linked issues.

### Startup reconciliation

At the start of every afk-agent run, before scanning, the agent:

1. Lists open issues that carry `agent-pr-open` or `agent-in-progress` and whose body references an `afk/issue-N-*` task branch.
2. For each, checks the linked PR's state via `gh pr list --head <task-branch> --state all --json state,number`.
3. If the PR is `MERGED`: close the issue with a brief reconciliation comment, remove all `agent-*` labels.
4. If the PR is `CLOSED` (not merged): apply `agent-failed`, remove `agent-in-progress` / `agent-pr-open`, comment "PR was closed without merging — needs human review."

This ensures no issue is left in a stale `agent-*` state across runs.

## Claim Lock

Locks use both labels and comments.

Labels:

- `agent-claimed`
- `agent-in-progress`
- `agent-pr-open`
- `agent-failed`

Before claiming, the agent re-reads the issue and aborts if any of those labels is already present.

## Branches

- Batch branch: `agent/<theme-slug>` — created/synced from `main` at the start of a batch. Lifetime spans the whole batch; merged to `main` by a human.
- Task branch: `afk/issue-<number>-<slug>` — branched **off the batch branch**, not main.
- Task PR base: the batch branch.
- Task PR merge: `gh pr merge --auto --squash` — auto-merges into the batch branch once required checks pass. **No draft PRs.**
- Batch → main: human review and merge. The agent never opens a PR with base = main.

If the batch branch already exists at run start, `git fetch && git checkout` it before creating task branches.

## PR Body Contract

Every task PR body must contain:

- run id and link back to the source issue
- `Closes #<issue>` on its own line (creates PR↔issue link; fallback auto-close when batch → main)
- first failing test behavior + commands that passed (from the TDD phase)
- AC verification rollup: `L1 N · L2 N · L3 N · L4 N`
- explicit list of L4 ACs that need human verification before the batch branch merges to main

## Test Gates

Default commands (override per repo via `AGENTS.md` or `package.json` if present):

```bash
pnpm lint
pnpm test
pnpm build
```

For UI changes, the agent additionally runs the AC verification step (see `TDD_REQUIREMENTS.md`), which exercises L3 acceptance criteria in a headless browser and captures snapshots/screenshots as evidence.

## Acceptance Criteria Verification

After lint/test/build pass:

1. The agent classifies each pending AC as L1 (grep/AST), L2 (test), L3 (browser), or L4 (human-only). Explicit author tags (`[L1]`/`[code]`/`[L2]`/`[test]`/`[L3]`/`[browser]`/`[L4]`/`[manual]`) override the heuristic.
2. The agent runs the matching check for every L1/L2/L3 AC and records concrete evidence (file:line, test name + output, screenshot path).
3. For every AC that passes, the agent edits the issue body and flips that exact line's `- [ ]` to `- [x]`. AC text is never modified. L4 items are never ticked.
4. The agent posts an AC verification report comment with one bullet per AC: text, level, status (pass / fail / skipped-L4), evidence reference.

### Partial-fail policy

If **any** L1/L2/L3 AC fails verification:

- do not create a PR
- add `agent-failed`, remove `agent-in-progress`
- post the **failure comment** (see "Comment Timeline")
- leave the issue body unchanged (do not tick any boxes for this issue in this run)

L4 items are flagged in the PR body and completion comment but never block PR creation or auto-merge.

## Failure Policy

If implementation, lint/test/build, or AC verification fails:

- do not create a PR
- add `agent-failed`
- remove `agent-in-progress`
- post the failure comment

## Concurrency

- Max parallel issues in one wave: 2
- Before claiming, re-read the issue and abort if any of `agent-claimed`/`agent-in-progress`/`agent-pr-open`/`agent-failed` is present.
- Before flipping AC checkboxes, re-fetch the issue body and abort if it changed since the last read.
